1. 先理解威胁模型

使用 pi2web 前必须接受一个前提：获得配对码的人，实际上获得了运行 pi2web 那个用户的 Shell 权限。

  • Terminal 是以 pi2web 进程用户身份运行的完整宿主机 Shell，可以访问 Workspace 之外的文件和继承到的环境变量。
  • Agent 本身也能读写文件、执行命令，这正是它的用途。
  • Workspace 路径只决定初始 cwd，不是安全边界，也不是沙箱。
  • pi2web 不校验 Origin / Host，方便配合内网穿透，但也意味着不要依赖这两项做防护。
不要把端口直接暴露到公网。

正确做法是先建立一条可信通道（SSH、私有网络或带访问控制的 HTTPS 反代），再在通道内访问服务。

2. 配对码与限流机制

pi2web 的认证很直接：除 Web 静态资源、/health 和 /api/v1/auth/login 外，所有请求都需要 Authorization: Bearer <token>。

  • 配对码只在首次启动或轮换时显示一次，服务端只保存 SHA-256 hash，文件权限 0600。
  • Web UI 必须手动输入配对码；连接成功后才询问是否保存到 localStorage。
  • 同一来源地址在 60 秒窗口内失败 10 次即被锁定，锁定时间从 60 秒起按次翻倍，最长 15 分钟，返回 429 与 Retry-After；WebSocket 升级同样受限；一次成功配对立即清零。
限流按 TCP 来源地址统计。

通过 devtunnel、Cloudflare Tunnel 或反向代理访问时，所有客户端共用同一个计数桶：一个人不断输错，可能把其他人也锁在门外。

Shell
# 怀疑配对码泄漏时立刻轮换
pi2web --rotate-access-token

3. 方案一：SSH 端口转发（推荐）

最简单也最安全：服务继续只监听 127.0.0.1，由 SSH 建立加密通道。

Shell
# 在客户端机器上执行
ssh -N -L 11318:127.0.0.1:11318 user@dev-host

# 然后访问 http://127.0.0.1:11318

因为访问地址是 localhost，浏览器把它视为安全上下文，通知与麦克风也能正常使用。Android 手机可以用支持端口转发的 SSH 客户端达到同样效果。

4. 方案二：Tailscale 等私有网络

如果需要长期从手机访问，私有网络比每次开隧道更省事。把服务绑定到 tailnet 地址，只有加入同一网络的设备可达：

Shell
pi2web --host 100.x.y.z --port 11318

建议配合 tailnet 的 ACL 限制哪些设备可以访问该端口。注意通过纯 HTTP 的私有 IP 访问时不是浏览器安全上下文，通知与麦克风会被禁用；Tailscale 的 HTTPS 证书功能可以解决这一点。

5. 方案三：devtunnel 与内网穿透

没有公网 IP、也不方便装 VPN 时，devtunnel、Cloudflare Tunnel 一类工具可以直接把本地端口发布成 HTTPS 地址。pi2web 不校验 Origin / Host，所以可以直接使用。

  • 务必启用隧道服务自身的访问控制（登录、白名单或访问策略），不要发布成完全匿名的公开地址。
  • 限流会按隧道出口地址统计，多人共用时请特别注意。
  • 不用时关闭隧道，比让它一直挂着更安全。

6. 方案四：nginx + HTTPS 反向代理

如果你已经有一台带证书的服务器，也可以自己反代。关键是正确转发 WebSocket 升级头，并在代理层加一道访问控制。

nginx
server {
    listen 443 ssl http2;
    server_name pi.example.com;

    ssl_certificate     /etc/letsencrypt/live/pi.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/pi.example.com/privkey.pem;

    # 额外的访问控制：客户端证书、Basic Auth 或 IP 白名单
    allow 203.0.113.0/24;
    deny all;

    location / {
        proxy_pass http://127.0.0.1:11318;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 3600s;
        proxy_send_timeout 3600s;
    }
}

proxy_read_timeout 要足够长，否则长时间运行的 Agent 会被代理断开连接。反代后所有请求共用同一个来源地址，限流计数也会合并。

7. 上线检查清单

  • 服务是否仍绑定在 127.0.0.1 或私有地址，而不是 0.0.0.0？
  • 访问通道是否有独立于配对码的第二层控制（SSH 密钥、tailnet ACL、隧道策略或代理鉴权）？
  • 配对码是否只在可信设备上保存到 localStorage？
  • 是否使用 HTTPS 或 localhost，以便启用浏览器通知与麦克风？
  • 是否知道如何在泄漏时立即轮换配对码？
  • 运行 pi2web 的用户权限是否已按最小化原则收敛（例如不用 root）？
