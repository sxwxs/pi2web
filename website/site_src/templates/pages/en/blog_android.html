1. Why a native client

The browser already covers most scenarios, but a native app is nicer on a phone: persistent login state, system notifications, better keyboard and scrolling behaviour, and background connections. It talks to the same pi2web service, so nothing extra needs to be deployed.

The server uses the real SDK.

pi2web runs the real @earendil-works/pi-coding-agent SDK and reuses the Pi CLI's ~/.pi/agent models, authentication, and settings. MockBackend exists only for automated tests.

2. Build

There is no prebuilt APK yet, so build it yourself with Android Studio or from the command line:

Shell
git clone https://github.com/sxwxs/pi2web.git
cd pi2web/android
./gradlew assembleDebug
# Output in app/build/outputs/apk/debug/

Exact toolchain requirements (JDK, Android SDK versions) and connection notes live in android/README.md; the full feature list is in ANDROID_APP_FEATURES.md.

3. Connect and pair

  1. Make sure the phone can reach the pi2web address. The service listens on 127.0.0.1 by default, so you usually need an SSH tunnel, a private network such as Tailscale, or a tunnel with access control.
  2. Enter the server address in the app, for example http://100.x.y.z:11318.
  3. Enter the pairing code. It is shown only on first startup or rotation; if you lost it, run pi2web --rotate-access-token.

Trade-offs between connection methods are covered in the secure remote access guide.

5. Practical tips

  • The phone is best for following up and intervening; start large refactors from the desktop.
  • Mobile networks switch often, but WebSocket sequence de-duplication and incremental replay mean short drops do not lose messages.
  • The pairing code is equivalent to shell access — store it only on your own device and keep a lock screen enabled.
  • When you stop using a device, rotate the pairing code to revoke it.
