01
AGENT CONTROL

The full agent lifecycle, not a preview.

pi2web starts agents through the real Pi SDK, so what you can do in the browser closely matches what you can do in the Pi terminal.

AVAILABLEprompt · steer · follow-up

Conversation and intervention

Send prompts, steer a running agent, queue follow-ups, or abort the current run.

AVAILABLEnavigate · fork · undo

Session branching

Navigate the session tree and fork or undo from any node, keeping Pi's native branching semantics.

AVAILABLEmodel · thinking · compact

Runtime settings

Switch models and thinking levels at any time, and compact the context when a session grows long.

AVAILABLEarchive · lazy start

Lazy start and archive

After a restart agents are unloaded; a Pi session is created on first use. Archiving only sets a database flag and never touches session files.

The event channel also handles

  • WebSocket sequence de-duplication
  • Exponential backoff reconnects
  • Incremental replay and snapshot recovery
  • Extension UI events and responses
  • Collapsible retry, tool, and thinking blocks
  • Completion notifications for every known agent

Models, provider authentication, and quota come from your local ~/.pi/agent. pi2web provides no model capability.

02
SECURITY MODEL

Simple access control, explicit boundaries.

There is exactly one layer of authentication. Whoever holds the pairing code effectively holds a shell as the service user, so storage, rate limiting, and exposure all matter.

01

Pairing code

Printed once on first startup; only its SHA-256 hash is stored, in a 0600 file.

02

Typed manually

The web UI never reads the code from a URL and never receives it from the server.

03

Opt-in storage

Only after a successful connection are you asked whether to save it in localStorage.

04

Failure lockout

Ten failures per source in 60 seconds trigger a lockout that doubles up to 15 minutes, returning 429 and Retry-After.

05

Rotation

pi2web --rotate-access-token invalidates the old code immediately and prints a new one.

06

Local by default

Binds 127.0.0.1. Use an SSH tunnel, Tailscale, or an HTTPS reverse proxy for remote access.

!

Terminals are not sandboxes. They are full host shells running as the pi2web process user and can reach files outside the workspace as well as inherited environment variables. Read the secure remote access guide.

03
WORKSPACE & TERMINAL

Code stays within reach.

Workspaces provide directory browsing and file reads, terminals provide a real shell, and both appear in the same list as your agents.

TREE

Directory browsing

Browse the tree per workspace, page through text files, and get a clear notice for binary content.

MENTION

Reference files with @

Type @ in the composer to browse and reference workspace files or directories directly in a prompt.

PTY

Interactive terminals

Right-click a directory to open a shell with input, resize, output snapshots, clear, and close.

RECONNECT

Refresh and reconnect

Reloading the browser reattaches to running terminals; the last 512 KiB of output is replayed.

LIMITS

Resource limits

Up to eight terminals per server process. Terminals live only in process memory and end when the service exits.

SESSIONS

Session index

A lightweight SQLite index powers listing, sorting, and pagination without copying message content.

04
NOTIFICATIONS

Get told the way you prefer.

Browser notifications, spoken summaries, and email can be combined. Voice and email are disabled until you configure them explicitly.

WEB PUSH

Browser notifications

Once granted, every known agent can notify you on completion. Requires a secure context (localhost excepted).

SUMMARY

Spoken summaries

A summary LLM condenses the final answer, TTS streams sentence by sentence, and concurrent sessions queue instead of overlapping.

STT

Speech input

With --voice-stt-model configured, a microphone button appears; transcripts are inserted into the composer and never auto-sent.

MAILDISPATCH

Email notifications

When an agent settles, pi2web submits transactional mail to MailDispatch; a 202 means it entered the durable queue.

AGGREGATION

Aggregation window

Wait a configurable number of seconds after the first completion so nearby completions share one email.

CONTENT

Body control

Choose whether to include the final reply, the session name, and the working path. Settings persist in the server database.

05
API & CLIENTS

An API and an Android app, beyond the web UI.

Except for static assets, /health, and the login endpoint, every request needs Authorization: Bearer <token>. Responses are always { data } or { error }.

REST/api/v1/workspaces · /agents · /sessions

Resources

Create and query workspaces, agents, and sessions; browse trees and read files or stat info.

REST/api/v1/agents/:id/prompt · steer · abort

Agent commands

Send instructions, switch model and thinking level, name sessions, fork, compact, and answer extension UI.

WS/api/v1/ws

Event stream

Supports sequence, replay, snapshot, fromNow, and agent commands.

WS/api/v1/terminals/:id/ws

Terminal channel

Input, window resize, output snapshots, and exit events.

Android client

  • Native Kotlin + Jetpack Compose app
  • Same API and pairing code as the web UI
  • Sessions, agents, and streaming conversations
  • Build instructions in android/README.md
  • Streaming PCM playback and recording not wired yet

The full capability list lives in ANDROID_APP_FEATURES.md in the repository.

SELF-HOSTED & FREE

The remote shell is free — the models are yours.

pi2web is MIT-licensed open source. It hosts no code, proxies no model requests, and uploads no sessions. You bring a working Pi Coding Agent configuration and provider.
