SECURE REMOTE ACCESS

Access pi2web securely: SSH tunnels, Tailscale, and HTTPS reverse proxies

pi2web has exactly one layer of authentication, and its terminals are full host shells. This guide explains the threat model and shows four workable options: SSH tunnels, Tailscale, devtunnel, and an nginx HTTPS proxy.

1. Understand the threat model first

Before using pi2web you must accept one premise: whoever holds the pairing code effectively holds a shell as the user running pi2web.

  • Terminals are full host shells running as the pi2web process user, with access to files outside the workspace and to inherited environment variables.
  • The agent itself can read, write, and execute — that is the point of a coding agent.
  • A workspace path only sets the initial cwd. It is not a security boundary and not a sandbox.
  • pi2web does not validate Origin or Host, which makes tunnels convenient but means you cannot rely on those headers for protection.
Never publish the port directly.

Establish a trusted channel first — SSH, a private network, or an HTTPS proxy with access control — and reach the service inside that channel.

2. Pairing code and rate limiting

Authentication is straightforward: except for static assets, /health, and /api/v1/auth/login, every request needs Authorization: Bearer <token>.

  • The code is shown once on first startup or rotation; only its SHA-256 hash is stored, in a 0600 file.
  • The web UI requires manual entry and only asks about localStorage after a successful connection.
  • Ten failures from one source address in 60 seconds trigger a lockout that starts at 60 seconds and doubles up to 15 minutes, returning 429 with Retry-After. WebSocket upgrades are limited too; one success resets the counter.
Limits are per TCP source address.

Behind devtunnel, Cloudflare Tunnel, or a reverse proxy, every client shares one bucket — one person repeatedly typing the wrong code can lock everyone out.

Shell
# Rotate immediately if you suspect the code leaked
pi2web --rotate-access-token

3. Option one: SSH port forwarding (recommended)

The simplest and safest option. The service keeps listening on 127.0.0.1 while SSH provides the encrypted channel.

Shell
# On the client machine
ssh -N -L 11318:127.0.0.1:11318 user@dev-host

# Then open http://127.0.0.1:11318

Because the address is localhost, the browser treats it as a secure context, so notifications and the microphone keep working. On Android, an SSH client with port forwarding achieves the same result.

4. Option two: Tailscale or another private network

For regular phone access, a private network beats opening a tunnel every time. Bind the service to the tailnet address so only devices on the network can reach it:

Shell
pi2web --host 100.x.y.z --port 11318

Pair this with tailnet ACLs restricting which devices may reach the port. Note that plain HTTP over a private IP is not a browser secure context, so notifications and the microphone stay disabled; Tailscale's HTTPS certificates solve that.

5. Option three: devtunnel and similar tunnels

Without a public IP or a VPN, tools like devtunnel or Cloudflare Tunnel can publish the local port as an HTTPS URL. pi2web does not validate Origin/Host, so it works out of the box.

  • Enable the tunnel provider's own access control (login, allow list, or policy). Do not publish an anonymous public URL.
  • Rate limiting counts the tunnel egress address, which matters when several people share it.
  • Close the tunnel when you are not using it rather than leaving it running.

6. Option four: nginx + HTTPS reverse proxy

If you already run a server with certificates, proxy it yourself. The key parts are forwarding WebSocket upgrade headers and adding a second layer of access control.

nginx
server {
    listen 443 ssl http2;
    server_name pi.example.com;

    ssl_certificate     /etc/letsencrypt/live/pi.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/pi.example.com/privkey.pem;

    # Extra access control: client certs, basic auth, or an IP allow list
    allow 203.0.113.0/24;
    deny all;

    location / {
        proxy_pass http://127.0.0.1:11318;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 3600s;
        proxy_send_timeout 3600s;
    }
}

Keep proxy_read_timeout generous or long agent runs will be disconnected by the proxy. Behind a proxy all requests share one source address, so rate-limit counters merge as well.

7. Before you go live

  • Is the service still bound to 127.0.0.1 or a private address rather than 0.0.0.0?
  • Does the channel add a second control independent of the pairing code (SSH keys, tailnet ACLs, tunnel policy, proxy auth)?
  • Is the pairing code stored in localStorage only on trusted devices?
  • Are you on HTTPS or localhost so notifications and the microphone work?
  • Do you know how to rotate the pairing code immediately if it leaks?
  • Does the pi2web user run with least privilege (definitely not root)?
