Using the pi2web web UI

Once paired, the browser is a full agent workbench. This guide covers workspaces, agents, conversation control, file references, terminals, recovery, and notifications.

1. Connect and pair

Open the service address (http://127.0.0.1:11318 by default) and type the pairing code. It is never read from URL parameters and never injected by the server. After a successful connection the page asks whether to store it in localStorage; if you decline, the code lives only in the page's JavaScript memory and is gone after a refresh.

The server address, the current workspace/agent, and the event sequence cursor are kept in localStorage so a refresh restores your view quickly.

2. Workspaces

A workspace is a local directory plus a name. It gives agents an initial working directory and enables file browsing.

  • Browse the directory tree and read text files with pagination; binary files show an explicit notice.
  • Type @ in the composer to browse and reference files or directories directly in a prompt.
  • Right-click a directory to open an interactive terminal at that path.
A workspace is not a sandbox.

It only sets the initial cwd. Terminals and agents run as the pi2web process user and can reach files outside the workspace.

3. Creating and managing agents

When creating an agent you can start a new session or resume an existing one. Agents and terminals share one list so you can switch between them in a single view.

  • Lazy start: after a restart agents are unloaded; the Pi session is created when you read messages or send a command, and concurrent requests share one startup.
  • Stop agent: releases the running session while keeping metadata, so the next use restarts it automatically.
  • Archive: right-click an agent to archive it. This only sets archived_at in the database and never moves, renames, or deletes Pi session files.

4. Conversation control

The composer supports four operations that map to Pi's native semantics:

ActionEffectWhen to use
PromptStarts a new agent run.Ask for a task or a question.
SteerInjects guidance into the current run.Correct course without restarting.
Follow-upQueues work for after the current run.Let it finish, then continue.
AbortStops the current run.Requirements changed or it went off track.

Thinking, tool calls, retries, and extension UI events are collapsible, so long conversations do not drown in tool output. Model and thinking level can be switched at any time and apply to subsequent runs.

5. Branching and compact

  • Session naming — the name shows up in lists, notifications, and spoken summaries.
  • Tree navigate — walk through the session's history nodes.
  • Undo / fork — go back to a node, or branch off from it.
  • Compact — compress the context of a long-running session.

These operations act on Pi's JSONL session files; pi2web's SQLite database only keeps a rebuildable index.

6. Terminals

Terminals use node-pty on the server and xterm.js in the browser, and give you a full host shell.

  • Input, window resize, clear, close, and reconnect after a browser refresh.
  • The last 512 KiB of output is retained for reconnect replay.
  • Up to eight terminals per server process.
  • Terminals live only in process memory and end when pi2web exits or restarts.

7. Notifications and voice

The "settings" dialog in the navigation bar toggles email notifications and configures the aggregation window, whether to include the agent's final reply, and whether to include the session name and working path. These settings live in the server database and apply to every client.

Browser notifications require permission and a secure context (localhost excepted); once granted, every known agent can notify you. If the server has voice configured, an "enable voice" button appears and plays the PCM16 or MP3 audio pushed by the server. With an STT model configured, a microphone button appears as well; transcripts are inserted into the composer and never sent automatically.

8. Reconnect behaviour

The web UI receives events over WebSocket and de-duplicates them by sequence. After a disconnect it reconnects with exponential backoff and requests an incremental replay or a snapshot based on the stored cursor, so a brief network drop, a Wi-Fi switch, or a sleeping phone does not lose output.

Browser and Android differences.

Custom Pi TUI components cannot be rendered generically in a browser, and the Android client does not yet implement streaming PCM playback or recording UI.
